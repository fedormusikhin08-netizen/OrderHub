# OrderHub — учёт заказов интернет-магазина

Итоговый проект по контрольным точкам **КТ31–КТ39** («Коллекции, LINQ, перечислители и итераторы в C#»).

Консольное приложение, которое последовательно обрастает возможностями:
очередь и стек заказов, история на `LinkedList`, склад на `Dictionary`,
сортировка каталога, отчёты на LINQ, ленивые итераторы и собственная
коллекция `CircularBuffer<T>` с поддержкой `foreach`.

## Как собрать и запустить

```bash
dotnet build OrderHub.sln
dotnet run --project src/OrderHub
```

Требования: .NET SDK 8.0 или новее.

## Ответы на вопросы

1. Queue<T> и Stack<T> отличаются порядком выдачи. В очереди первым уходит тот, кто первым пришёл (Enqueue в конец, Dequeue из начала), в стеке наоборот, последний пришёл — первый вышел (Push и Pop с вершины). В OrderHub очередь — это pendingQueue: заказы должны обрабатываться в порядке поступления. Стек — undoHistory: отменять логично последнее действие. Обе структуры дают O(1) на добавление и извлечение, так что выбор тут не про скорость, а про дисциплину доступа.

2. AddLast возвращает LinkedListNode<T>, то есть ссылку на только что вставленный узел. Если сохранить её в current, следующая вставка AddAfter(current, order) делается за O(1), без поиска. Через Find пришлось бы идти по цепочке (O(n)) и передавать значение для сравнения, а для Order сравнение идёт по ссылке, то есть найти «такой же» заказ по данным не выйдет. Поэтому в InitHistory узел запоминается сразу: current = orderHistory.AddLast(order).

3. Индексатор stock[key] для отсутствующего ключа бросает KeyNotFoundException: словарь не может вернуть значение типа int, которого нет, и не хочет молча подсовывать default. Ловить исключение ради проверки — плохая идея, для этого есть TryGetValue: один поиск, bool-результат и out-значение. В WarehouseService так сделано и в Receive, и в Sell, и в TryGetStock, поэтому отсутствие товара — это false и сообщение в консоль, а не падение программы.

4. IComparable<T> реализует сам тип, и это его естественный порядок: у Product CompareTo сравнивает цены, поэтому products.Sort() без аргументов работает. IComparer<T> — отдельный класс-сравнитель, который передаётся в Sort(new NameComparer()) или Sort(new PriceDescComparer()), сам Product при этом не меняется. Если тип не реализует ни IComparable<T>, ни старый IComparable, Sort() упадёт с InvalidOperationException (внутри ArgumentException от Comparer<T>.Default): стандартному компаратору нечем сравнивать. Правда, на списке из нуля или одного элемента сравнений не будет, и ошибки тоже.

5. LINQ-запрос — это описание, а не результат. Пока его не начали перебирать, Where и OrderBy не выполняются вообще. Обход стартует при foreach, ToList, Count, Any, First, Sum. Причём каждый новый перебор запускает запрос заново, поэтому если исходная коллекция поменялась, результат будет другим. В ReportService цепочки заканчиваются ToList, так что там запрос уже выполнен, а если вернуть IEnumerable без ToList, он выполнится только у вызывающего.

6. IGrouping<TKey,TElement> — это группа из GroupBy: у неё есть Key и она сама является IEnumerable<TElement>. От обычной коллекции отличается именно ключом, а по элементам можно ходить foreach и применять обычный LINQ: Count, Sum, Average, Where, Select. В SummarizeByCategory на группе считаются g.Count() и g.Average(...), без промежуточного списка и ручного цикла.

7. Join строит по второй последовательности хеш-таблицу ключей, потом идёт по первой и на каждый ключ выдаёт все совпадения. Это inner join: пара без совпадения в результат не попадает. Если у клиента несколько заказов, получится несколько строк, по одной на заказ, поэтому дальше я делаю GroupBy по имени и Sum, и сумма собирается правильно. У Петровой в SeedData заказов несколько, и в топе она первая как раз из-за суммы.

8. Вызов метода с yield return не запускает его тело: создаётся перечислитель, а код идёт по шагу на каждый MoveNext. В Orders() стоит while(true), но за один MoveNext отдаётся один заказ, и цикл продолжается только когда попросят следующий. Take(N) после N элементов перестаёт вызывать MoveNext и освобождает перечислитель, поэтому бесконечный цикл не успевает раскрутиться. А вот Orders().ToList() или Count() на таком итераторе действительно повиснут.

9. IEnumerable<T> наследует обычный IEnumerable, а у того GetEnumerator возвращает IEnumerator, а не IEnumerator<T>. Это разные типы, поэтому одной реализацией оба интерфейса не закрыть, нужна явная: IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();. Без неё класс не скомпилируется, потому что контракт интерфейса не выполнен. В CircularBuffer она есть, и заодно не торчит лишним методом в публичном API.

10. В кольцевом буфере next — индекс для следующей записи, size — сколько элементов лежит сейчас. Индекс самого старого получается так: (next - size + capacity) % capacity. Прибавляю capacity, чтобы до взятия модуля не уйти в минус. Дальше иду вперёд по кольцу: index = (index + 1) % capacity. В Reverse стартую с (next - 1 + capacity) % capacity и иду назад.

11. Девять отдельных заданий — это девять раз «создай проект и напиши заготовку», и связи между темами не видно. В одном проекте каждый этап опирается на предыдущий: одни и те же заказы, товары и клиенты, отчёты читают коллекции, итераторы порождают те же заказы, CircularBuffer показывает, как foreach устроен внутри. Плюс нормально тренируется Git: ветки на этап, слияния через PR. Защищать цельную программу сложнее, чем девять кусков, но и понимание проверяется честнее.
